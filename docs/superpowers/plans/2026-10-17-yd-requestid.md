# yd 实施计划：RequestID 的安全与性能

> 需求来源（用户原话）：
> 「RequestID插件要进行更安全、效率更高、性能最好的算法并进行优化」

## 0. 需求差异说明

只读需求基线未涵盖本节，本文件即差异说明。

## 1. 现状与问题

`middleware.RequestID` 从请求头（默认 `X-Request-Id`）**无条件取值**，取不到就用 `crypto/rand`
生成 UUIDv4（手写十六进制编码，无 `fmt`）。生成路径本身写得不错：一次随机读 + 一个栈上数组 + 一次 `string()`。

**安全性问题（按严重程度）**：

| # | 问题 | 后果 |
|---|---|---|
| **S1** | **无条件信任客户端头** | ①**日志注入**：ID 会进入日志，若含换行/控制字符可在 console 格式里伪造日志行；②**关联欺骗**：攻击者可指定 ID 把不同请求在追踪系统里串成一条，或覆盖他人请求的 ID；③**日志放大**：1 MB 的头值会被原样存进上下文并反复打进日志 |
| S2 | 无条件**回显**到响应头 | Go 的 `net/http` 会把响应头值里的换行替换成空格，因此 CRLF 注入被标准库挡住；但**仍不该回显未校验的输入**——依赖下游实现来兜底不是设计 |
| S3 | 无长度上限 | 同上，日志放大 |

**性能上**：每请求一次 `crypto/rand.Read`（系统调用）+ 一次 36 字节 `string` 分配。
在极高 QPS 下，随机数读取会成为可观成本，值得测量后优化。

## 2. 设计

### 2.1 安全（优先于性能）

- **`TrustIncoming bool`，默认 `false`**：默认**不信任**客户端提供的 ID，一律自行生成。
  需要链路透传时显式开启——把「信任外部输入」变成写下来的决定。
- **开启后仍必须校验**：长度 ≤ 128；字符集限定 `[A-Za-z0-9._:-]`（无空白、无控制字符、无换行）；
  校验失败**丢弃客户端值、改用自生成 ID**，并计数（不是逐条 Warn——否则又是一条放大通道）。
- **绝不回显未校验的输入**：回显的只能是「自生成的」或「校验通过的」值。
- **生成 ID 的长度固定**（36 字节 UUID 文本），不随输入变化。

### 2.2 性能（测量驱动）

先测再优化，候选手段：

1. **随机字节批量取用**：从 `crypto/rand` 一次取 1 KiB 存到每 P 的缓冲里，逐请求消费，
   把系统调用摊薄到 1/64。安全性权衡写在文档里（缓冲内容是密码学随机，只是**分批**取，
   不降低单个 ID 的不可预测性；缓冲随 P 生命周期，不跨进程）。
2. **避免多余分配**：ID 用 `[36]byte` 栈上构造后一次 `string()`（现状已如此，保持）；
   `c.SetHeader` 若会复制字符串，评估能否复用。
3. **不引入 UUID 库**：现有手写编码已是最少分配的实现，引入第三方库只会更慢更重。

**验收用基准说话**：`BenchmarkRequestID`（含"命中客户端头"与"自生成"两条路径），
优化前后对比 ns/op 与 allocs/op；**没有实测提升的不合并**。

### 2.3 可选：时间有序 ID（UUIDv7）

UUIDv4 完全随机，在日志系统里按 ID 排序没有时间意义；UUIDv7（RFC 9562）前 48 位是毫秒时间戳，
**对日志索引与追踪更友好**，且仍保留随机部分。提供 `Options.Version`（默认 v4，可选 v7），
并在文档里说明取舍：v7 会**泄露粗粒度创建时间**（毫秒），对某些场景是信息泄露。

## 3. 测试

| 场景 | 期望 |
|---|---|
| 默认（不信任） | 忽略客户端头，生成新 ID |
| 信任 + 合法头 | 沿用，且回显一致 |
| 信任 + 含换行/控制字符 | **丢弃**，改用自生成 |
| 信任 + 超长（>128） | **丢弃**，改用自生成 |
| 客户端 ID 与生成 ID 的格式 | 回显的永远是合法值 |
| 上下文可取 | `RequestIDKey` 能取到同一个值 |
| 并发 | `-race` 干净，ID 不重复（10 万个 ID 无碰撞） |
| `crypto/rand` 失败 | 回退路径仍产出合法且不重复的 ID |
| 性能 | 基准对比，自生成路径 allocs ≤ 1 |

另外要有一条**对抗性测试**：构造 `X-Request-Id: "abc\r\nX-Injected: 1"`，
断言响应头里**没有** `X-Injected`、日志里**没有**伪造的行。

## 4. 验收

1. 默认不信任客户端 ID；开启信任后非法值一律被替换；
2. ID 不可预测（`crypto/rand`，回退路径有明确说明）；
3. 基准证明性能不劣于现状（若做批量随机，须有显著提升才合并）；
4. `-race`、`gofmt`、`vet` 全绿；
5. 向后兼容：`RequestID(header string)` 签名保留，新能力经 `RequestIDOptions` 提供。

## 5. 已知取舍

- **默认不信任入站 ID**：会改变现有"透传"的行为，但安全默认应当如此；
  需要透传的部署显式开启即可。这是**有意的行为变更**，须在发布说明中标注。
- **UUIDv7 默认不启用**：时间戳泄露是真实代价，默认仍用 v4。
- **不追求"绝对零分配"**：ID 最终要作为字符串存进上下文并回显，一次 `string()` 分配不可避免；
  目标是**除这一次之外零分配**。
