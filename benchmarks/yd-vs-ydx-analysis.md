# yd 与 ydx 基准口径差异分析

本文解释为什么 `benchmarks/json`、`benchmarks/base64` 与 ydx 仓内的组件基准
（`ydx/benchmarks/json`、`ydx/benchmarks/base64`）给出的排名不一致，并记录
2026-10-23 的三轮优化（`ydx/base64 v0.1.8`→`v0.1.9`、`ydx/json v0.1.9`→`v0.1.10`、
`ydx/log v0.1.7`→`v0.1.8`）。

## 结论摘要

1. **两套基准的载荷与对比集合不同**，绝对 ns 不可直接比较：
   - yd 的 JSON 使用 7 字段 `record`（含 `time.Time`、`Email`，`Score` 为
     `float64(i)/3` 的长小数，n=1 时是单元素数组）；
   - ydx 的 JSON 使用 5 字段 `benchUser`（`Score` 为 `98.5` 短小数，`one` 是单个对象）；
   - yd 的 Base64 覆盖 32 B 并加入 cloudwego/base64x；ydx 的 Base64 从 16 B 起，
     只对比标准库与 cristalhq。
2. **长小数已补齐**：v0.1.9 为超出精确短范围的尾数与指数形式加入非舍入缩放快速
   路径（最多 19 位有效数字，超出时用 d 与 d+1 判定截断尾部），单个长小数记录从
   220.7 降到 209.5 ns（-5.1%），n=100/n=1000 相对 v0.1.9 快约 1.1%–1.2%。
   n=1 的单记录对链接布局敏感，本轮约 317 ns，落后 go-json 约 11%；多记录吞吐
   才是该路径的主要收益。
3. **Base64 32 B 已转为领先**：v0.1.8 把短输入 SIMD 阈值提到 64 后，32 B 回到标量
   路径；v0.1.9 增加两个 12 字节 XMM 头部 + 8 字节向量尾部的全向量编码内核，并让
   32–63 字符解码先走 128 位块内核，32 B 编码/解码降到 **5.68/10.51 ns**，双双
   超过 cloudwego（7.59/11.87）与 cristalhq（9.77/12.63）。
4. **日志低指标已优化**：v0.1.8 的纯 ASCII 8 字节快速转义、64 字节 `Field` 与毫秒
   时间戳缓存，使 dynamic Info 从 131.7 降到 95.7 ns、prebound 从 124.5 降到
   90.8 ns、禁用 dynamic 从 7.97 降到 6.30 ns；prebound 已快于 zerolog（96.8 ns）。
5. **测量框架差异**：yd 的对比基准通过函数指针调用各实现（对全部实现公平），
   ydx 的组件基准直接调用 API；在 32 B 上函数指针额外约 0.7–1.4 ns，绝对数会高于
   ydx README，但相对排名仍以同一框架为准。

## JSON

### 载荷差异

| 项 | yd `benchmarks/json` | ydx `benchmarks/json` |
|---|---|---|
| 字段数 | 7（`created`、`tags`、`id`、`score`、`name`、`email`、`active`） | 5（`name`、`tags`、`id`、`score`、`active`） |
| 时间字段 | `time.Time`（固定值 `2026-10-18T12:00:00Z`） | 无 |
| Score | `float64(i)/3`，最长 17 位小数 | `98.5`，短小数 |
| n=1 形态 | 单元素数组 | 单个对象 |

因此 ydx README 的 `Unmarshal/one`（118.6 ns）与 yd 的
`Unmarshal/n=1`（优化前 316 ns）不是同一件事。

### 长小数根因

对同一 7 字段载荷做单对象直接调用（参考主机，`GOMAXPROCS=1`）：

| 载荷 | ydx/json v0.1.8 | goccy | 说明 |
|---|---:|---:|---|
| `Score=98.5`（短小数） | 200 ns | 205 ns | ydx 领先 |
| `Score=7.0/3`（长小数） | 255 ns | 221 ns | ydx 落后 |

长小数 `2.3333333333333335` 的尾数超过 2^53，v0.1.8 的
`parseShortFloatField` 放弃后，依次重复 `parseNumberBytes`、`parseShortDecimalFloat`
扫描，最后调用 `strconv.ParseFloat`。v0.1.9 改为单遍 `scanFloatField`，一次扫描
同时完成语法校验与短范围转换，长小数不再多付两遍扫描。v0.1.10 再把超出精确短范围的
尾数与指数形式交给 `parseDecimalOrFloat64`：最多 19 位有效数字走非舍入缩放，超出时
用 d 与 d+1 两次转换判定截断尾部是否影响结果，仍不确定才回退 strconv。

### 优化前后（参考主机，同一轮交替采样）

| 场景 | v0.1.9 | v0.1.10 |
|---|---:|---:|
| 7 字段单对象 `Score=4/3`（长小数） | 220.7 ns | **209.5 ns** |
| yd `Unmarshal/n=1`（0/3，短小数） | 约 300 ns | 约 312 ns |
| yd `Unmarshal/n=100` | 19,168 ns | **18,934 ns** |
| yd `Unmarshal/n=1000` | 191.1 µs | **189.1 µs** |

n=100/n=1000 的收益来自长小数转换；n=1 只含一个短小数，却因新增函数/表改变了
链接布局而慢约 4%，属于单记录基准的布局敏感性，而非浮点路径本身。多记录吞吐是
该优化的目标口径。与 go-json 相比，n=100/n=1000 仍保持约 15%/10% 的领先。

## Base64

### 载荷与对比集合差异

| 项 | yd `benchmarks/base64` | ydx `benchmarks/base64` |
|---|---|---|
| 最小尺寸 | 32 B | 16 B |
| 对比实现 | 标准库、cloudwego/base64x、cristalhq | 标准库、cristalhq |
| 调用方式 | 函数指针（所有实现一致） | 直接调用 API |

### 32 B 阈值问题

v0.1.7 的编码 SIMD 阈值是 28 B、解码是 32 字符，32 B 输入因此进入 SIMD。
参考主机实测（直接调用）：

| 操作 | SIMD 路径（v0.1.7） | 标量路径 | cloudwego |
|---|---:|---:|---:|
| Encode 32 B | 9.60 ns | **7.91 ns** | 6.51 ns |
| Decode 44 字符 | 12.88 ns | **11.47 ns** | 10.44 ns |

v0.1.8 把阈值统一提高到 64（编码 64 B、解码 64 字符），32 B 回到标量路径。
yd 的函数指针框架下：

| 指标 | v0.1.7 | v0.1.8 | cloudwego |
|---|---:|---:|---:|
| Encode 32 B | 10.20 ns | **8.80 ns** | 7.47 ns |
| Decode 32 B | 13.93 ns | **12.86 ns** | 11.51 ns |

v0.1.9 新增低启动成本的 32 B 全向量内核后：

| 指标 | v0.1.7 | v0.1.8 | **v0.1.9** | cloudwego | cristalhq |
|---|---:|---:|---:|---:|---:|
| Encode 32 B | 10.20 ns | 8.80 ns | **5.68 ns** | 7.59 ns | 9.77 ns |
| Decode 32 B（44 字符） | 13.93 ns | 12.86 ns | **10.51 ns** | 11.87 ns | 12.63 ns |

编码内核由两个 12 字节 XMM 头部加一个 8 字节向量尾部组成，一次写满 44 个字符且
不调用标量尾部；解码先由 128 位块内核处理前 32 个字符，再由标量循环收尾。两者都
通过专用入口直接分派，避免通用包装层的固定成本。32 B 已从弱项转为两个方向的领先：
编码快于 cloudwego 约 25%，解码快约 11%。

## 方法学建议

- 对比 ranking 时保持**同一框架、同一载荷、同一进程模型**；不要跨 README 比较绝对 ns。
- 新增实现或修改阈值后，至少覆盖 **16 B、32 B、64 B、1 KiB** 与**短/长小数**两类 JSON 载荷。
- 函数指针带来的固定开销在小尺寸上占比很高；报告绝对数时应注明调用方式，
  或同时给出直接调用参考值。
